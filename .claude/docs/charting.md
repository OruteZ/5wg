# Charting

채보 — 곡에서 악기별 연주 타이밍을 뽑아 박 인덱스로 저장하는 일.

`weapons.md`의 "타이밍 — 곡이 발사를 결정한다"가 기획이고, 그 문서의 미정 항목
**"채보 데이터 포맷과 추출 파이프라인"**을 이 문서가 이어받는다.

이 문서는 문답으로 확정한 내용만 담는다. **"미정"으로 적힌 것은 아직 결정되지 않은 것이지
생략된 것이 아니다** — 채우지 말고 물어야 한다.

## 한 줄 요약

**곡은 믹스된 파일 하나가 아니라 stem 여러 개다.** 플레이어가 고른 악기의 stem만 들리고,
그 악기의 노트가 곧 발사 타이밍이다. 무기를 얻을수록 곡이 두꺼워진다.

## 데이터

```
ChartAsset (ScriptableObject)   ← 에셋 하나 = 곡 하나. 곡 식별은 에셋 자신
  double     bpm
  Track[]    tracks
    InstrumentTrack instrument  ← 열거형 10종 (킥·스네어·하이헷·크래시·탐·
                                   베이스·기타·어쿠스틱·건반·신스)
    AudioClip       stem        ← 악기별 1:1
    int[]           notes       ← 곡 시작부터 누적된 서브박 인덱스
```

### 왜 이 모양인가

- **곡 전체를 담은 클립 필드가 없다.** 안 고른 악기는 들리면 안 되므로 믹스본을 틀 수 없다.
  재생은 트랙별 `AudioSource`를 동시에 출발시키는 것이다.
- **노트는 `(마디, 박, 서브박)` 삼중항이 아니라 누적 서브박 인덱스 하나다.** 마디·박·서브박은
  나눗셈으로 언제든 나오고 `BeatTick.SubIndex`가 이미 같은 형태다. 삼중항으로 두면
  세 값이 서로 어긋난 상태가 표현 가능해진다.
- **곡 식별자를 따로 두지 않는다.** 에셋 하나가 곡 하나이므로 트랙 열거형은 곡 안에서만
  유일하면 된다. "다른 곡의 같은 악기"는 다른 에셋이라 충돌하지 않는다.
- **`subPerBeat` 필드가 없다.** 16분 고정이다(아래 "해상도"). 필드로 두면 `BpmClock` 설정과
  어긋날 수 있다.
- **시작 오프셋 필드가 없다.** 음원을 0초가 비트 0이 되게 잘라서 받기로 했다(아래 "음원").
- **"항상 들리는 트랙" 표시가 없다.** 드럼처럼 늘 재생돼야 하는 파트가 있을 수 있지만,
  이 브랜치는 무기와 엮지 않아 검증할 방법이 없다. 필요해지면 `bool` 한 줄이다.

### 해상도는 16분 고정

`BpmClock`의 `subPerBeat`가 4다. 하이헷이 16분으로 달리는 게 락 밴드 편성의 기본이고,
그보다 잘게 쪼갠 연주는 자동공격에서 발사로 구분되지도 않는다. 해상도를 올리면 검출
노이즈가 그대로 노트가 된다.

에셋에는 **스냅된 인덱스만** 남긴다. 원본 초는 안 들고 있고, 대신 추출 도구가 "이 노트는
37ms 어긋나서 스냅했다"는 리포트를 뱉는다. 스냅이 의심스러우면 그 리포트를 본다.

## 음원

**WAV로 받는다.** mp3는 디코딩 시 파일 앞에 인코더 지연이 붙는다 — LAME 기준 1,700샘플
남짓, 44.1kHz에서 **약 39ms**다. 파형 편집기에서 아무리 정확히 잘라도 Unity가 읽으면 그만큼
밀려 있다. 128 BPM의 16분음표가 117ms이니 한 노트의 3분의 1이 통째로 밀리고, 이건
"잘랐는데 왜 안 맞지"로 하루를 태우는 종류다.

**0초가 비트 0이다.** 사람이 잘라서 준다. 그래서 오프셋을 맞추는 절차가 없고, 사람이 넣을
값은 BPM 하나뿐이다.

**stem은 전부 같은 지점에서 잘라야 한다.** 트랙마다 따로 자르면 한 악기만 앞서 들리고,
"어느 악기가 밀렸는지"를 귀로 찾아야 해서 디버깅이 고약하다. 원본 곡에서 한 번 자른
지점을 전 트랙에 똑같이 적용한다.

**곡마다 트랙 수가 다른 것은 정상이다.** SUNO의 stem 분리는 보통 4~6트랙까지만 깔끔하게
나온다. 한 곡에서 10종이 다 나오지 않아도 되고, `weapons.md`의 "세트리스트는 같은 악기
구성의 곡들로 짠다"가 이미 그 상황을 전제한다.

### stem은 커밋하지 않는다

`Assets/_Proejct/Sounds/Stems/`에 두고 `.gitignore`로 막는다. 곡당 수십 MB에 악기별로
나뉘어서 세트리스트가 늘면 저장소가 통째로 무거워진다. **커밋하는 것은 stem이 아니라
거기서 뽑아낸 채보다.** 팀 공유가 필요해지면 그때 Git LFS를 붙인다.

그래서 **저장소를 새로 받으면 그 폴더가 아예 없고, `ChartAsset`의 `stem` 참조가 전부 비어
있다.** `.meta`도 같이 무시되므로 같은 파일을 다시 넣어도 GUID가 새로 생겨 **자동으로 복구되지
않는다** — 손으로 다시 물려야 한다.

지금은 개발자가 혼자고 stem이 로컬에만 있으면 되므로 이 비용을 받아들인다. 채보의 노트는
stem과 무관하게 살아 있어서 잃는 것은 참조뿐이다. 사람이 늘거나 CI에서 곡을 다뤄야 하면
그때가 Git LFS를 붙일 시점이다.

## 클록과 재생

`BpmClock`은 음원을 모른다. `Play()` 시점의 `AudioSettings.dspTime`을 비트 0으로 잡는
순수 클록이다. 그래서 **`ChartPlayer`가 클록과 `AudioSource`들을 둘 다 들고**, 클록이
앵커를 잡는 것과 같은 `dspTime`에 `PlayScheduled`로 전 트랙을 동시 출발시킨다.

`dspTime`이 곧 오디오 하드웨어 시계라 이 방식은 표류하지 않는다. 트랙이 몇 개든 같은
시계를 쓰므로 서로 어긋나지도 않는다.

- `BpmClock`을 고쳐 `AudioSource`를 갖게 하지 않는다. 그 클래스의 "순수 클록" 성격이 깨진다.
- `AudioSource.timeSamples`에서 박을 역산하지 않는다. 프레임 단위로만 갱신돼 오히려 거칠다.

**`BpmClock.bpm`을 `int`에서 `double`로 바꿨다.** SUNO 곡이 정수 BPM일 가능성은 낮은데,
잘라버리면 곡 후반에 채보가 무너진다. 128.4 BPM 클릭 트랙으로 실제로 재본 값이다.

| | |
| --- | --- |
| 128.4 BPM 한 박 | 467.29 ms |
| 128로 잘못 돌릴 때 | 468.75 ms — 박당 **1.46 ms** |
| 16분음표 하나 | 116.8 ms |
| 14초 지점 누적 오차 | 43.8 ms — 16분음표의 **38%** |
| 3분 지점 누적 오차 | **563 ms** — 16분음표 **4.8개** |

박당 1.46ms는 눈에 안 띄지만 누적된다. 곡이 끝날 무렵엔 발사가 다섯 박자 가까이 밀린다.

`Quantizer`가 이미 `double bpm`을 받으므로 필드와 프로퍼티만 바꾸면 됐다.
`Beat/`는 외부 템플릿 유래 폴더지만 이건 예외로 뒀다.

곡과 클록을 같은 시각에 출발시키려면 앵커를 미래로 잡을 수 있어야 해서 `BpmClock.PlayAt(dspTime)`도
같이 넣었다. 기존 `Play()`는 호출 순간을 비트 0으로 박아버려서 `PlayScheduled`와 맞출 방법이 없다.

**안 고른 악기의 stem도 재생하되 볼륨을 0으로 둔다.** 아예 안 트는 것과 소리는 같지만,
나중에 그 악기를 획득했을 때 곡 중간부터 페이드인할 수 있다 — 레벨업 카드로 신스를 얻는
순간 곡에 신스가 들어오는 그림이 공짜로 나온다.

## 온셋 검출

두 알고리즘을 **둘 다 C#으로 구현하고 같은 음원에 돌려 비교한 뒤** 하나로 확정한다.
어느 쪽이 이길지는 실제 stem을 재보기 전에는 모른다.

### 에너지 포락선

**무엇을 보나** — 짧은 창마다 신호의 에너지를 재고, 그 값이 직전 대비 급격히 오르는 지점을
온셋으로 본다. 소리가 갑자기 커지는 순간을 찾는 것이다.

| | |
| --- | --- |
| 이길 때 | 어택이 뚜렷한 타악기. 킥·스네어·하이헷·크래시 |
| 질 때 | 어택이 흐린 소리. 페이드인하는 신스 패드, 레가토로 이어지는 기타. **소리가 이미 나는 중에 음만 바뀌면 에너지가 안 변해서 못 잡는다** |
| 비용 | FFT 불필요. 샘플을 훑고 제곱합. 가장 싸다 |

### 스펙트럴 플럭스

**무엇을 보나** — 창마다 주파수 분포를 구하고 직전 창과 비교해, 각 대역에서 **늘어난 양만**
합산한다. 소리의 크기가 아니라 "성분이 바뀐 정도"를 본다.

| | |
| --- | --- |
| 이길 때 | 음높이가 바뀌는 것이 곧 새 노트인 경우. 에너지가 그대로인 레가토 연주를 잡는다 |
| 질 때 | 비브라토·트레몰로처럼 성분이 계속 흔들리면 헛검출이 는다. 창 크기가 **시간 해상도와 주파수 해상도를 맞바꾼다** — 창을 키우면 주파수는 정확해지고 언제 일어났는지는 뭉개진다 |
| 비용 | 창마다 FFT. 에너지 방식보다 훨씬 무겁고 구현도 길다 |

### 왜 에너지 쪽을 먼저 재보나

**stem이 이미 악기별로 갈려 있다는 게 결정적이다.** 킥 트랙에는 킥만 있으므로 "이 트랙에서
소리가 커지는 순간"이 곧 "킥이 쳐진 순간"이다. 여러 악기가 섞인 믹스에서 필요한 주파수
분해가 여기서는 필요 없을 수 있다. 싼 쪽을 먼저 재보고 못 잡는 악기가 나오면 그때 붙인다.

`weapons.md`가 "온셋 검출 정확도를 곡 하나로 먼저 재본 뒤 편집 툴이 얼마나 필요한지
정한다"고 순서를 정해둔 것과도 맞는다.

### 두 방식 공통

- **임계값은 절대값이 아니라 상대값으로 잡는다.** 최근 구간의 중앙값 대비로 봐야 곡의
  셈여림 변화에 안 무너진다.
- **최소 간격으로 뭉갠다.** 한 번의 타격이 여러 창에 걸쳐 검출되므로, 16분 간격보다 짧은
  연속 검출은 하나로 합친다.

## 검증

수치와 귀를 둘 다 쓴다. 귀는 20~30ms 이하 어긋남을 잘 못 잡고, 수치는 "듣기에 그루브가
어색한" 것을 못 잡는다.

**수치** — 스냅 오차 분포. 평균·최대 ms, 임계 밖 노트의 비율.

**귀** — 트랙 하나씩 본다. stem을 가운데, 메트로놈 클릭을 왼쪽, 검출된 온셋 클릭을
오른쪽 채널로 갈라 재생한다. 어긋나면 플랜징처럼 들려서 몇 ms 차이도 바로 잡힌다.
전 트랙 동시 재생은 **stem끼리 어긋나지 않았는지** 보는 별도 버튼으로 둔다.

## 저작

**전용 편집 윈도우를 만들지 않는다.** 인스펙터에서 노트 배열을 보고 고친다.

검출은 **버튼이 아니라 메뉴**가 됐다. Alchemy가 인스펙터를 그리고 있어서 커스텀 에디터로
버튼을 얹으면 그쪽과 부딪힌다. 프로젝트 창에서 `ChartAsset`을 고르고 `Tools/Charting/`에서
고른다 — 에너지로 검출 / 플럭스로 검출 / 두 방식 비교(노트는 안 건드림). 리포트는 콘솔로 간다.
확인 재생은 `ChartPlayer`의 `[Button]` 그대로다.

검출이 잘 맞으면 손댈 일이 거의 없어서 파형 에디터는 헛수고가 된다. 정확도를 재본 뒤에도
상세한 노트 설계가 필요하다고 판단되면, 인스펙터를 키우는 대신 **외부 편집 툴이나 편집
전용 씬**으로 간다.

## 파일 배치

| | |
| --- | --- |
| `Scripts/Runtime/Charting/` | `ChartAsset` `InstrumentTrack` `ChartPlayer` — 런타임에 남는 것 |
| `Scripts/Editor/Charting/` | 온셋 검출·리포트 — 에디터에서만 돈다 |
| `Scenes/Charting.unity` | 검증 전용. Build Settings에 넣지 않는다 |

검출 코드를 런타임 파일의 `#if UNITY_EDITOR` 안에 넣지 않는다. 이 저장소가 그 관례를
쓰긴 하지만(`WeaponLevelData`의 셀프체크) 그건 20줄 안팎이라 **대상 타입 바로 옆에 있어야
의미가 있는 것**이다. FFT를 포함해 200줄쯤 되는 검출기는 성격이 다르다. `Editor`라는 이름의
폴더는 asmdef 없이도 Unity가 에디터 어셈블리로 보내므로, 런타임 빌드에 FFT가 실려 나가지 않는다.

`Charting.unity`는 `BeatSample.unity`에 얹지 않고 새로 판다. 그쪽은 외부 템플릿이 준
데모라 뭐가 왜 있는지 모르는 오브젝트가 섞여 있고, 거기 얹으면 내 문제인지 템플릿
문제인지 가르기 어려워진다.

## 이 브랜치의 완료 조건

1. 두 알고리즘이 C#으로 돌고, 같은 음원에 대해 **스냅 오차를 나란히 리포트**한다
2. 합성 클릭 트랙으로 파이프라인이 도는 것 확인
3. **실제 stem 하나로 정확도 측정** — 음원이 오면. 안 오면 여기서 멈춘다
4. 메트로놈 좌 / 검출 온셋 우 분리 재생으로 귀 확인

**무기와 엮지 않는다.** 채보를 읽는 `IFireTiming` 구현체는 다음 브랜치다.

합성 클릭 트랙은 ffmpeg로 만든다. **다만 클릭은 어택이 완벽해서 어떤 검출기든 100% 맞힌다** —
파이프라인이 도는지만 증명하고 정확도는 증명하지 못한다. 정확도 측정에는 진짜 stem이 필요하다.

### 클릭 트랙 다시 만들기

`Sounds/Stems/`는 커밋되지 않으므로 저장소를 새로 받으면 이것들도 없다. 한 줄로 다시 만든다.

```bash
ffmpeg -y -f lavfi -i "aevalsrc='0.7*sin(2*PI*1000*t)*exp(-45*mod(t,0.5))':d=16:s=44100" -c:a pcm_s16le Click_120bpm.wav
```

`mod(t, 박길이)`가 매 박 0으로 돌아가고 `exp(-45*x)`가 급감쇠해서 클릭이 된다. 박 길이만
바꾸면 다른 BPM이 나온다 — 128.4 BPM이면 `mod(t,0.46728971962616822)`.

클릭 위치는 이렇게 잰다. `silence_end`가 각 클릭의 시작이다.

```bash
ffmpeg -i Click_120bpm.wav -af "silencedetect=noise=-40dB:d=0.05" -f null -
```

### 지금까지 확인한 것

**시간 계산** — 120 BPM 클릭이 정확히 0.5초 간격으로 찍히고, `ChartAsset`이 계산하는
서브박 0.125초 × 4와 일치한다. 128.4 BPM 클릭으로 정수 BPM의 누적 오차도 실측했다(위 표).

**예약 재생** — `Charting.unity`에서 재생 15.4초 지점에 클록과 오디오를 나란히 쟀다.

| | |
| --- | --- |
| 클록 경과 ↔ stem 재생 위치 | **0.01 ms** |
| 클록 ↔ 메트로놈 / 온셋 클릭 | 0.02 ms |
| 트랙끼리 | 0.01 ms 이내 |

44.1kHz에서 샘플 하나가 0.023ms이니 **샘플 단위로 붙어 있다.** `PlayScheduled` +
`PlayAt`로 같은 `dspTime`에 출발시키는 설계가 그대로 동작한다.

**온셋 검출** — 두 방식을 클릭 트랙 두 개에 돌렸다.

| 음원 | 방식 | 정답 대비 | 스냅 오차 평균 | 최대 |
| --- | --- | --- | --- | --- |
| 120 BPM | 에너지 | 32/32 | 7.4 ms | 11.6 ms |
| | 플럭스 | 32/32 | **2.3 ms** | 11.6 ms |
| 128.4 BPM | 에너지 | 35/35 | 7.2 ms | 11.6 ms |
| | 플럭스 | 35/35 | **1.7 ms** | 11.6 ms |

놓침도 헛검출도 없고, 반칸(58~62ms)을 넘긴 노트도 없다. 비정수 BPM에서도 같다.

**이 결과로 알고리즘을 고를 수는 없다.** 클릭은 어택이 완벽해서 둘 다 100%가 나온다 —
파이프라인이 도는 것만 증명됐다. 승부는 어택이 흐린 악기에서 갈리므로 진짜 stem이 필요하다.

### 검출을 두 번 고친 곳

처음 돌렸을 때 **31/32에 스냅 오차 평균 18.9ms**였다. 둘 다 원인이 분명했다.

**검출이 계통적으로 일렀다.** 부호를 보니 전부 음수(에너지 −18.9ms, 플럭스 −13.5ms)였다.
프레임 `f`는 `[f*hop, f*hop+window)` 구간을 보는데 그 시각을 **창의 시작**으로 잡고 있었다.
창 하나가 23ms이므로 그만큼 이르게 나온다. **창의 중심**을 그 프레임의 시각으로 바꿨다 —
MIR의 관례이기도 하다. 오차가 에너지 7.4ms, 플럭스 2.3ms로 줄었다.

**곡 첫 박의 타격을 놓쳤다.** 검출 함수가 직전 프레임과의 차이라서 0번 프레임에는 값이
없었다. 0초가 비트 0이라는 규칙 때문에 첫 박에 타격이 있는 것이 오히려 정상인데, 그걸
통째로 흘리고 있었다. 0번 프레임을 "무음에서 올라온 것"으로 보게 고쳤다.

두 방식에 남은 오차 차이(7.4 vs 2.3ms)는 창 함수 때문이다. 플럭스는 해닝 창을 씌워
가운데에 무게가 실리고, 에너지는 직사각 창이라 창 전체가 같은 무게다. 방식별로 다른
보정값을 두면 더 줄일 수 있지만, 합성 음원 하나에 맞추는 것이라 하지 않았다.

## 미정

- **어느 알고리즘으로 확정할지** — 재보고 정한다. 이 문서의 목적 자체다.
- **편집 툴이 얼마나 필요한가** — 정확도를 재본 뒤. 외부 툴인지 편집용 씬인지도 그때.
- **"항상 들리는 트랙"** — 드럼처럼 무기 보유와 무관하게 재생돼야 하는 파트가 있는가.
  무기와 엮는 브랜치에서 정한다.
- **곡 전환 처리** — 세트리스트에서 다음 곡으로 넘어갈 때의 클록·채보 교체 (`weapons.md`).
